serial_triton: an exact LIF neuron over L tokens, 4.6 to 6.9 times faster

Prerequisites: the LIF neuron, the surrogate gradient, backpropagation through time.

A LIF neuron that carries its membrane over all L tokens must run step by step. The reference kernel of SpikingJelly does this slowly. serial_triton keeps the same neuron and the same serial loop, and removes the time that the GPU spends on waits.

L is the number of tokens (2048 in the study). The repo uses T for the ticks per token, so this page uses L for the tokens.

Measured on one RTX 5090 at [L, B, D] = [2048, 16, D]. Each time is the median of 10 passes of one neuron site. Source: REPORT.md, section 1.

1. The neuron stays the same

These are the equations of SpikingJelly's ParametricLIFNode with a soft reset. Here q = 1/tau is the leak, and theta is the threshold.

h_t = v_{t-1} + (x_t - v_{t-1}) * q     charge
s_t = 1 if h_t >= theta else 0          fire
v_t = h_t - theta * s_t                 soft reset

serial_triton computes these three lines in the same order, in float32. So the spikes cannot differ. The method is not a new neuron, and it is not parallel in time.

2. Why the reference kernel is slow

The reference kernel asks the memory for x_t, waits, computes one step, and then asks for x_{t+1}. The wait is about 0.4 µs per step in the forward pass and 0.95 µs in the backward pass. With 2048 steps the waits alone are about 2.8 ms.

The proof is in the two sites. Site out has twice the data of site in, but the time is almost the same: 3.089 ms against 2.847 ms. A kernel that is limited by data would need twice the time. This kernel is limited by waits.

Analogy (the filing cabinet). A trip to the cabinet is slow. The reference kernel makes one trip per file. The new kernel asks for 32 files in one trip, and then works through them at the desk.

3. The three changes, step by step

The toy numbers are made up: q = 0.5, theta = 1, 8 time steps, and the loss is the sum of the spikes. A script computed every toy value and checked the gradients against PyTorch autograd.

Eight steps: the neuron on toy numbers, the old kernel with one wait per step, the new kernel with loads ahead, the tape, the 8-bit code, the backward pass, no second read of x, and the bytes per step.

4. Why training and inference do not slow down

The math is the same, so nothing must be learned again. The forward pass is exact. On the real activations of all 12 blocks (24 neuron sites) the kernel gave 0 wrong spikes.

The gradient stays close to the exact one. With the 8-bit tape the cosine to SpikingJelly's gradient is 0.9996 at in and 0.9997 at out. With the float32 tape it is 1.0000.

The neuron now costs about three copies of its input. A plain copy of the tensor takes 0.135 ms at in and 0.267 ms at out. The whole forward and backward pass of the neuron takes 0.415 ms and 0.677 ms. The kernels move bytes at 1.25 to 1.44 TB/s, and a plain copy reaches 1.4 to 1.5 TB/s.

With the micro-batch of 2 that the repo trains with, the times are 0.208 ms and 0.256 ms against 1.413 ms and 2.119 ms (6.8× and 8.3×).

Inference. Inference needs only the forward pass. SpikingJelly's forward pass takes 0.886 ms at in and 0.972 ms at out. The forward kernel of serial_triton alone takes 0.328 ms at out with the 8-bit tape, and 0.287 ms when it writes no tape. The function in neuron.py always writes the tape today.

What this page does not claim. The study timed one neuron site, not a whole training step. The model has 24 sites. If every site saved what the table shows, the saving would be 12 × (2.432 + 2.412) = 58 ms per forward and backward pass at B = 16. This is arithmetic, not a measurement.

5. How to call it

from neuron import serial_triton   # autoresearch/soft_reset_LIF_experiment/neuron.py

# x: [B, L, D] float32 on the GPU, tau: [D] (expand a scalar tau to D values)
spikes, v_last = serial_triton(x, tau, theta=1.0, U=32, BLOCK=64, nw=2, tape="u8", bf=1)
  • U=32: the number of time steps that the kernel loads ahead.
  • tape: "u8" is the fastest. Use "h16" if the leak is trained and its gradient must be accurate. Use "h32" for a gradient equal to SpikingJelly's.
  • bf=1: the tensors are batch-first, as in the model. Then no transpose is necessary.
  • For site out the best block shape is BLOCK=512, nw=8.

6. Limits

  • The kernel is not connected to src/. It is in the autoresearch folder only.
  • The study neuron has a soft reset and carries the membrane over tokens. The trained checkpoint has a hard reset, 4 ticks per token, and a reset per token. The hard-reset variant of the kernel gave the same speed-up (0.416 / 0.675 ms).
  • L must be a multiple of 32. tau must have D values. The kernel raises an error otherwise.
  • The 8-bit tape gives about 3 % relative error on the leak gradient of one channel. The float16 tape gives 0.1 to 0.3 %.
  • The speed-up falls for very wide layers: 1.6× at 100k neurons and 1.4× at 400k neurons. There both kernels wait for memory bandwidth.
  • At the micro-batch of 2, Python is the limit (0.23 ms of the pass). A faster kernel cannot help there.
  • 5× at site out is not possible with float32 tensors. A tape with zero bits would give 0.605 to 0.615 ms, and 5× needs 0.618 ms. The smallest tape that keeps the gradient cosine above 0.99 has 5 bits.

7. Common mistakes

  • "It is parallel in time." No. Each neuron still runs its 2048 steps one after the other. Only the memory waits overlap.
  • "The 8-bit tape changes the spikes." No. The forward pass uses the exact float32 membrane. Only the surrogate gradient reads the rounded value.
  • "A smarter parallel method must be faster." Not at this size. The study tried 23 methods. Each extra pass over x costs 0.07 ms at in and 0.14 ms at out, and that is a third of the whole serial neuron.

8. Check your understanding

The float16 tape costs 0.03 ms more than the 8-bit tape at in, but 0.07 ms more at out. Why is the cost at out about twice as large?

Answer

The kernel is limited by the number of bytes it moves. Site out has twice the neurons (1536 against 768), so one more tape byte per step is twice the bytes. The forward pass writes the byte and the backward pass reads it.
